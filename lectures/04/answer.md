# 第4回 解答

## 宿題

- 取り組んだレベル：発展
- やったこと：SWE-bench Verified の公開データと、対応する Astropy の issue 3件を読み、問題の性質、検証体制、採点方法を比較した。ここではコードの修正・実行やベンチマークのスコア測定は行っていない。
- データセット：[SWE-bench Verified](https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified)。実際のソフトウェアの issue を、リポジトリへの修正で解決する500件の評価セットである。[公式概要](https://www.swebench.com/verified.html)

### 読んだ問題と難しさ

以下の instance ID が Verified のデータに含まれることを確認し、元の issue 本文で再現例と要求を読んだ。問題文の全文転載はせず要約した。3件とも Astropy なので、これだけでデータセット全体の難易度分布は推定できない。

1. **astropy__astropy-12907**：モデルの結合を入れ子にすると、本来独立な入出力まで依存しているという行列が返る。平坦な結合と入れ子の結合の意味が同じなのに結果が異なる問題である。解決には、再帰的なモデル結合と依存行列の組み立てを追跡し、既存の依存関係を保つ必要がある。着手方法は再現例から行列の変化を追うことだが、実装を見ずに修正できるとは判断できない。LLMには、例だけに合わせず他の結合でも整合する変更を作る難しさがある。[元のissue #12906](https://github.com/astropy/astropy/issues/12906)

2. **astropy__astropy-13033**：TimeSeries に time 以外の必須列を設定してその列を消すと、不足列を正しく説明しない例外文になる。例外を発生させるだけでなく、利用者が原因を理解できることが要求される。解決の入口は必須列の一覧と現在の列を比較する処理で、単一列・複数列・順序違いを区別するテストが必要と考える。LLMがエラー文だけ置き換えると、条件分岐の誤りを残す可能性がある。[元のissue #13009](https://github.com/astropy/astropy/issues/13009)

3. **astropy__astropy-13453**：表の出力で指定した数値書式が CSV 等では有効なのに、HTML では無視される。HTML 側の出力経路にも指定した書式を反映する課題である。まず出力形式ごとの処理の違いを調べる方針が考えられるが、入力表の値を変えてしまわず表示だけを修正する必要がある。LLMには、HTMLだけの個別修正と共通の書式処理をどう組み合わせるか、他の出力を壊さないかを確かめる難しさがある。[元のissue #13451](https://github.com/astropy/astropy/issues/13451)

上記の着手方法と難しさは問題文からの分析であり、実際に修正して通過したという報告ではない。

### 作成者・検証・採点

元の問題はオープンソースの利用者・開発者による issue と解決済み PR に由来する。**93人は全問題の作問者数ではなく、Python経験のある検証担当者数**である。OpenAI と SWE-bench の著者らは1,699件を調べ、各件を別々の3人が評価した。指示の曖昧さ、妥当な解答を不当に落とすテスト、その他の問題を確認し、3人のうち最も厳しい判定を採用した。問題ありとされた割合は68.3%。残りから難しい課題を優先し、最終的に500件を構成したため、単純に1,699−500を「不良問題数」とは数えられない。採点は修正後のテスト実行で行い、不具合を検出するテストの成功と、既存機能の回帰テストの成功の両方を要求する。[作成・検証・採点の説明](https://openai.com/index/introducing-swe-bench-verified/)

### 講義の評価セットとの比較（結果）

| 観点 | 講義の評価セット | SWE-bench Verified |
|---|---|---|
| 規模・対象 | 10件の質問と期待する振る舞い | 500件の実リポジトリの修正課題 |
| 人による確認 | 講師1人のラベルを基準に比較 | 検証担当93人、各件3人の独立評価 |
| 判定 | 人とLLMによる基準別判定、一致率・要確認件数 | 修正したコードのテスト実行による解決判定 |
| 強み | 説明の分かりやすさ等の意味的な基準を扱える | 実際の動作と既存機能への影響を再現可能な手順で調べる |
| 注意点 | 少数例・ラベルの解釈差・採点LLMの変動 | テストの不足や過剰な制約、環境差、学習データへの混入 |

講義側の件数・作成者数・採点方法は「第4回宿題資料」の比較条件に基づく。演習を実行した結果や一致率はここでは報告していない。

### 気づき・疑問

テストによる判定にも、出題者の意図とテストが一致しているという前提がある。「テストを通る」と「現実の要求を満たす」を同一視できない。講義の評価セットでも、曖昧な基準は複数人で確認し、形式をコードで、説明の妥当性を人やLLMで判定する分担が有効だと考える。

また、調査時点で OpenAI は、Verified の残存するテスト問題や学習データへの混入を理由に同ベンチマークのスコア報告をやめている。138件の監査対象の59.4%に問題を見つけたという結果は、失敗しやすい課題を対象とした数字であり、500件全体の問題率とは扱えない。したがって本レポートでは、Verified を現在の万能な尺度ではなく、**評価セット自体を検証する方法を学ぶ事例**として位置づける。[その後の公式検証](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)

今後確かめたい点は、同じ修正を異なる環境で再評価した場合の再現性と、問題文だけから妥当と判断できる別解がテストに拒否されないかである。
